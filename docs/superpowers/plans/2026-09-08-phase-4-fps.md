# Phase 4 FPS Implementation Plan

> Execution: implement task-by-task in this session. The user authorizes implementation and prohibits commits; no execution approval or commits are required.

**Goal:** Two reserved players enter one externally authoritative training arena.

**Architecture:** Next.js owns authenticated reservation bootstrap and durable lifecycle leases. A separate Node service owns fixed-step Rapier simulation and WebSockets. A route-loaded Three.js runtime owns presentation and shared movement prediction; React owns menus and sampled HUD data.

**Tech stack:** Installed Next 16.3.4, React 19.2.8, Zod 4.5.4, Prisma 6.19; add Three.js, Rapier compat and ws, without replacing existing equivalents.

## Constraints and preflight

- Phase 4 only; no AI, enemies, waves, shops, progression, objectives or PvP.
- Preserve all prior work. No Git metadata exists; compare SHA256 against the temporary pre-edit manifest.
- Keep existing dependency junction; use a separate same-drive verification checkout if required by its documented cross-drive Webpack limitation.
- Read installed Next server/client, dynamic route, Route Handler and lazy-loading guides. Verify physics and rendering against installed declarations before implementation.
- No database snapshots or ammunition persistence. Only lifecycle, runtime ownership and expiring lease metadata are durable.

## Tasks

1. Shared simulation contract (`src/game/shared`): strict versioned schemas; validated configuration, industrial arena definitions, fixed accumulator, Rapier capsule controller, weapon authority. Tests exercise schema rejection, boundaries, jump, collision, fire rate, ammo, reload and occlusion.
2. Dedicated service (`services/game-server`): token verifier, match instance, capped transports and lifecycle callbacks. Signed reservations contain trusted participants; one-use join tickets bind runtime, room, identity and slot. Fixed simulation at 30 Hz and snapshots at 15 Hz. Tests use two actual WebSocket clients and deterministic simulation clocks.
3. Reservation handoff (`src/server/gameplay`, gameplay API routes, Prisma additive migration, lobby adapter): verify session/membership; claim a runtime lease atomically; provision the match via authenticated HTTP; issue a 30-second ticket. Lifecycle callbacks renew leases; expiry reconciliation and an authenticated sweep endpoint recover interrupted startup. Lobby no longer removes members owned by gameplay.
4. Client (`src/game/client`): bounded input history, acknowledgements, replay, measured correction smoothing and buffered remote interpolation; separate input/audio/render/network modules; async initialization and exhaustive disposal.
5. Gameplay route/HUD (`src/app/play/[matchId]`, `src/components/game`): route isolation, unsupported devices, loading/error/retry states, explicit pointer lock, sampled HUD, accessible settings and leave confirmation using existing primitives. Persist safe local settings and respect account motion/audio defaults.
6. Verify and document (`docs/phase-4-*`): focused and existing suites, protocol integration, real database migration validation where available, both builds, actual two-context browser checks and profiling. Record observations separately from remaining manual hardware/network checks; never claim unperformed checks.

## Review gates

- Incoming gameplay frames accept intent only, with sequence/tick windows and bounded per-command rate budgets.
- Both scene-ready clients are required for countdown. Simulation and firing are gated by the authoritative start.
- Connection retry obtains fresh tickets; runtime state and ammunition survive grace-period reconnect. A duplicate live slot is rejected.
- Shots originate at the authoritative eye and raycast world geometry before targets; players cannot take damage.
- Client resources and buffers remain bounded. Heartbeats do not depend on rendering or tab visibility.
- Tests assert public behavior and security boundaries, including malicious and delayed traffic.
